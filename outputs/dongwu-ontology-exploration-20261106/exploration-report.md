**已验证**仅指证据直接支持的字段、页面行为或指定样本事实；不自动推广为全系统约束。**较高可信推断**需要进一步反例检验。**待验证**包括未证实的业务规则和拟议建模方式。以下所有数量都是本账号在采集时点的返回值，不是全企业数据量保证。

## 2. 本轮做了什么

已验证（E01～E06）：读取 8 个列表/配置页面及 6 个详情页面，留存 83 次独立成功 API 响应，涉及 22 个不同路径；所有保留调用均为 HTTP 200、业务码 0。响应记录原有 84 条，其中 `details.json /requests/19` 是 `/requests/18` 的同一对象重复落盘，已从统计中排除。

已验证（E08、E09）：18 份实际加载的 JavaScript 资源中提取到 163 个不同 API 路径声明，其中 88 个不在上一阶段的 92 个保留路径内；两者并集为 180。**180 是路径证据的并集，不是已验证可用 API 数量**。本轮成功调用的 22 个路径中，5 个不在旧清单内。参数和业务含义须分别验证，不能由声明名称补全。

已验证（E02 及采集器）：中途一次本地文件写入失败使 `details.json.outcome=blocked`，此前响应仍成功且 JSON 完整；剩余请求在 E03 单独继续，后续保存改为临时文件加重命名。该失败不是云端业务拒绝。原始重复记录保留以便审计。

## 3. 核心发现及对建模的影响

| 结论 | 等级、证据 | 建模影响与边界 |
|---|---|---|
| 408 条生产记录均可通过 `order_artifacts_id` 精确接到对应订单构件，GUID、项目、订单一致 | 已验证：4 个计划 9155/9081/9153/163，共 10/167/144/87 条；E02 `/requests/7,9,11,13` 与 E06 `/requests/0..3`，E09 `identityJoins` | 分开维护两类资源身份；显式引用优先于编号/GUID。样本数量均为 1，不能证明批量行或全局一对一 |
| 生产任务页面是对同一计划的不同执行范围展示 | 已验证：计划 9081 详情均请求 getPlan，完整明细 167、current 8、my 68；E04 `/requests/1..8`、E05 `/requests/0..1` | 较高可信推断：当前证据支持任务作为执行视图，暂不建立独立 Task 主实体；全系统是否另有独立任务键仍待验证 |
| current 与 my 可在样本内解释为部门过滤 | 已验证：账号部门 68；current 的 8 条恰为 `department_current=68`；my 的 68 条恰为 `departments` 含 68，其中 32 条已完成；E04 `/requests/0/data/department`、E09 `taskComparison` | 较高可信推断：current 是当前处理范围，my 是参与范围。不能把 my 理解为“只含未完成任务”，也不能推广为全部账号的授权公式 |
| 一张报检单可包含多个计划的构件 | 已验证：34056 详情头 `plan_id="8939,9016"`，5 条成员中 4 条来自 8939、1 条来自 9016；E02 `/requests/14/data` | 报检与计划不能设置强制单值关系；列表中同单只返回 `plan_id="8939"`（E01 `/requests/24/data/list/0`），不能用列表投影覆盖详情事实 |
| 报检单及构件明细均含质量结果，探伤与质检有独立字段组 | 已验证：5 张详情覆盖状态 0/1/2/3/4，详见 E09 `inspectionDetails` | 明确区分单头汇总、明细结果、探伤与质检记录。未找到稳定独立结果 ID，也未证明两阶段完全独立状态机 |
| 包箱可包含跨订单成员 | 已验证：1614199 的 28 条来自订单 8903/8905（17/11），1614198 的 32 条来自同两订单（30/2）；E03 `/requests/7,9/data/samples` | 可否跨项目、一件能否重复入包及历史成员变更仍待验证；不得要求包箱必有一个非零 order_id |
| 包内构件与出库历史可一致，但发运单计数仍有差异 | 已验证：包 1622105 与当日项目 140 出库历史的 26 个 ID 完全相同，均引用发运 8514；重量 36201.21；发运列表为 27；E03 `/requests/4,5,11`、E01 `/requests/18/data/list/0` | 较高可信推断：27 可能包含一个包箱资源记录；未取得完整发运计数逻辑或 PDF 明细，禁止一律减 1 |
| 工艺设计元数据、图内名称和计划展开结构是不同表示 | 已验证：design 31 外层名称“正式-钢构生产管控流程”，`info.name` 含“（含探伤质检）”；计划图也含后者，并增加 features 等结构；E03 `/requests/1`、E02 `/requests/6/data/design_info` | 不能仅凭名称不同宣称版本变更；尚未发现不可变版本号。建模建议保留来源、采集时点、原图及内容摘要 |

## 6. 下一阶段建议

**待验证／建模建议**：现在可以进入概念评审，采用“业务概念—源记录—视图—观测证据”四层区分，以本轮明确的多计划报检、跨订单包装作为必要示例。先确定术语和身份边界，再逐条批准约束；不要按 180 个路径生成 180 个实体，也不要立即建库。

可继续自主读取的事项是列表计数差异、外围模块页面、批量/重排/重复 GUID 样本、报表口径及本地缺失桥接。需要业务方介入的是实物身份与批量计量的业务定义，以及后续写验证使用的专用测试环境、对象和角色；这些不是继续只读探索的前置条件。

本轮只新增当前输出目录，原项目及上一阶段交付的 240 份基线文件保持原样；具体校验记录见 [verification.json](evidence/verification.json)。未执行原应用同步、数据库修复或业务写操作。应用活文档：`docs: none`（应用行为未变；本轮业务分析文档单独交付）。
