# QQ 发货日期范围报表

## 目标

用户通过 QQ 私聊发送日期范围，机器人从本地 PostgreSQL 查询发货事件，并回传一个同时包含构件级明细和月度汇总的 Excel。

示例指令：

```text
发货明细 2026-07-01 至 2026-08-10
查询2026年7月1日到2026年8月10日发货信息
```

## 数据口径

- 查询 `component_status_event.status_type = 'shipping'` 且 `is_completed = true` 的事件。
- 日期按 `Asia/Shanghai` 时区判断，起止日均包含。
- 项目、构件编号、规格、部位、数量和重量优先读取 `SHIPPING_API_JSON` 事件快照；旧事件没有快照时回退构件主数据。
- 明细重量使用公斤原始精度；月度汇总换算为吨后保留三位小数。
- 月度汇总按“月份 + 项目”分组，并附每月合计和整个查询区间合计。

## Acceptance Criteria

- 合法的两个日期可被 QQ 指令解析；日期缺失、日期无效和起止倒置会返回明确提示。
- `发货对齐` 和“未发货构件”查询不会被本报表指令误拦截。
- 机器人返回一个 `.xlsx` 文件，且工作簿仅包含 `发货明细`、`月度汇总` 两个目标工作表。
- 明细与数据库发货事件逐行对应；汇总的数量、公斤重量和吨重量可由明细重新计算得到。
- 跨月范围分别生成各月项目汇总、月度合计，并生成区间合计。

## 抽象复盘

适用场景：同一份交付同时包含业务明细和统计汇总，且历史字段可能随主数据变化。

核心检查方法：先按统一的时区和日期边界取出一份明细事实集，再从这份明细派生所有月度、项目和区间汇总；历史属性优先读取事件快照，不能让明细和汇总分别查询、分别解释字段。

这能防止三类失败：明细与汇总过滤条件漂移、历史规格/重量被当前主数据覆盖、QQ 新指令误拦截既有“发货对齐”或“未发货”查询。

可迁移检查清单：确认日期是否双边包含、业务时区、事件快照回退规则、明细到汇总的数量血缘、月度/区间合计可重算性，以及新命令与已有命令的互斥样例。

对于数万行以上的多工作表 Excel，还要检查目标查看器的首张表和活动表行为。面向决策的汇总应放在首张并显式激活，不能只用解析库确认单元格存在；否则可能出现“文件内部有值，但 QQ/WPS 预览第二张表为空”的交付失败。
